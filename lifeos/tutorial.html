01
O intuito

Este projeto é duas coisas coladas: um arquivo público — páginas HTML independentes, publicadas de graça no GitHub Pages — e um painel privado, o LifeOS, onde a vida que alimenta esse arquivo é gerida.

A separação importa. O arquivo é o que você mostra: ensaios, mapas, diagramas, o que quer que sobreviva. O LifeOS é o que sustenta: as tarefas, as notas, o dinheiro, o calendário, os objetivos de longo prazo. Um alimenta o outro, mas só um é público.

Nada aqui depende de assinatura mensal, de um servidor que você aluga, ou de uma empresa continuar existindo.

O custo de manter isso no ar é zero na prática: GitHub Pages é gratuito para repositórios públicos, e o plano free do Supabase cobre folgadamente o uso de uma pessoa. Não há build, não há framework, não há pipeline. Um git push publica.

02
Tirar o armazenamento do cérebro

A ideia por trás do LifeOS é velha e simples: a cabeça é boa para pensar e ruim para guardar. Lembrar de pagar uma conta, de qual era mesmo aquele livro, de quanto se gastou no mês — nada disso exige inteligência, só exige retenção. E retenção ocupa espaço que fazia falta em outro lugar.

Enquanto uma tarefa vive só na memória, ela cobra atenção em intervalos aleatórios: na fila do mercado, no meio de uma conversa, às três da manhã. Ela volta porque a cabeça não tem como saber que já foi resolvida. Escrever em um lugar confiável desliga esse alarme.

O ganho não é lembrar de mais coisas. É parar de precisar lembrar.

Por isso o sistema cobre domínios que normalmente ficam em cinco aplicativos diferentes. Não é ambição de fazer tudo — é que memória fragmentada em cinco lugares continua sendo memória que você carrega, porque você ainda precisa lembrar em qual dos cinco aquilo estava.

E o segundo ganho aparece depois: material acumulado num lugar só vira algo que dá para consultar e cruzar. Seis meses de notas viram um corpo de texto onde se procura um padrão. Um ano de movimentações vira uma resposta sobre para onde o dinheiro realmente vai.

03
Os módulos

Seis áreas. O hub mostra o resumo de todas; cada uma tem a sua tela própria quando precisa de trabalho de verdade.

Hub
A visão geral: calendário, tarefas do dia, saldo, notas recentes, manifestações.
Finanças
Entradas e saídas, projeção de fatura de crédito, comparação entre meses.
Tarefas e Projetos
Kanban e lista. Toda tarefa pertence a um projeto — é o que impede virar caixa de entrada infinita.
Notas
Markdown, vinculado a um ou mais projetos. É a matéria-prima do arquivo público.
Eventos
Calendário, dentro do próprio hub. Compromissos com hora marcada, separados das tarefas.
Manifestações
Objetivos de longo prazo — o que você quer que seja verdade daqui a um ano.
Projeto é o eixo. Tarefas exigem um; notas podem ter vários; eventos podem ter um. É esse vínculo que deixa perguntar “o que existe sobre X?” e receber de volta as tarefas, as notas e os compromissos juntos.
04
Por que HTML cru

O arquivo público não usa framework, gerador de site estático ou tema. Cada entrada é um arquivo HTML com o seu próprio CSS dentro. Isso parece um passo atrás e é justamente o contrário.

Num gerador de site, toda página é obrigada a caber no molde do tema. Você escreve markdown e recebe de volta o mesmo layout de sempre. Serve para um blog; é uma camisa de força quando a página é o argumento.

  • Um diagrama que precisa de cores próprias — a página inteira se reorganiza em volta dele.
  • Uma linha do tempo que só funciona na horizontal, com escala não-linear.
  • Uma entrada que pede fundo claro quando todo o resto do arquivo é escuro.
  • Uma tabela interativa, um mapa, um pequeno jogo que explica um conceito.

Nada disso precisa de permissão. Você abre o arquivo e escreve. E porque cada página é autossuficiente, nenhuma pode quebrar outra — não existe CSS global a ser alterado por engano, nem dependência a atualizar. Uma página escrita hoje abre igual daqui a dez anos.

O preço é repetir estrutura entre páginas. O retorno é que nenhuma página é refém das outras.

O manifest.json é o que costura tudo: a capa lê esse arquivo e monta a listagem sozinha. Você nunca edita a capa à mão — publica a página, a entrada entra no manifest, o índice se atualiza.

05
O sistema junto com IA

É aqui que as duas metades se encontram, e é a parte mais fácil de subestimar.

A IA lê o seu sistema. O LifeOS expõe um servidor MCP — cole uma URL no seu cliente e a IA passa a consultar suas notas, tarefas, projetos, eventos e finanças por conta própria. Você para de copiar e colar contexto. Pergunta “o que eu já escrevi sobre isso?” e recebe uma resposta baseada no que você de fato escreveu, não no que o modelo imagina.

A IA escreve as páginas. Porque uma entrada é só HTML, uma IA consegue produzir uma inteira — diagrama, layout, estilo — a partir de um texto seu. Não há API a aprender, nem convenção de tema a respeitar: é HTML. A tela Publicar recebe o arquivo pronto e faz o commit.

A IA melhora o próprio sistema. O código é HTML, CSS e JavaScript sem build — o que significa que pedir “adiciona um gráfico de gastos por categoria” é um pedido que uma IA consegue atender de ponta a ponta, sem ambiente para montar antes. Os arquivos em docs/ existem para isso: são o contexto que faz uma IA entender o projeto antes de mexer nele.

O ciclo completo: você vive e registra no LifeOS → a IA lê pelo MCP e ajuda a pensar → o que valeu a pena vira uma página do arquivo → e a própria IA escreve essa página. O sistema deixa de ser onde as coisas ficam guardadas e passa a ser de onde o trabalho sai.
06
Configurar

Tudo abaixo fica no menu do hub — o botão no canto superior direito.

Senhas
A senha mestre abre tudo. Senhas extras abrem só as páginas do arquivo que você conceder a elas.
Publicar
Envia uma entrada nova pro arquivo. A aba Token é onde se cadastra o acesso ao GitHub.
Temas
Nove paletas para o painel. Criar a sua é copiar um arquivo CSS e trocar os valores.
MCP
A URL para conectar o sistema à sua IA, e o que ela passa a conseguir fazer.
Troque a senha mestre antes de qualquer outra coisa. Uma instalação nova nasce com uma senha padrão — ela existe só para você conseguir entrar na primeira vez. Enquanto não for trocada, qualquer pessoa que conheça o projeto entra no seu painel.
07
Por onde começar

A ordem abaixo evita o erro mais comum, que é tentar preencher o sistema inteiro num fim de semana e abandoná-lo na terça.

  • Troque a senha mestre. Em Senhas. É a única coisa realmente urgente.
  • Crie dois ou três projetos. Só os que você já tem de verdade — projeto é o eixo de todo o resto, e inventar projeto vazio só gera lista morta.
  • Use as tarefas por uma semana antes de mexer em mais nada. Se o hábito não pegar aqui, não pega no resto.
  • Depois, as notas. É o módulo que rende com o tempo: só faz sentido quando há material acumulado.
  • Conecte o MCP quando já houver algo para a IA encontrar. Conectar num sistema vazio não mostra nada.
  • Finanças por último. Exige constância diária e é o mais fácil de abandonar — deixe para quando o resto já for rotina.
A primeira página do arquivo pode esperar. O painel precisa virar hábito antes de ter o que publicar.
